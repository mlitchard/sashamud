● Here's what Quux does:

  Quux logout is purely a DB operation. It deletes the user's JWT token row from
   the tokens table. That's the whole thing — DELETE FROM tokens WHERE user_id =
   ? (or WHERE token = ? for self-logout). No channel, no event bus, no game
  state cleanup. The auth middleware then rejects subsequent requests because
  the token no longer exists.

  Route shape: AuthProtect "BEARER" :> Capture "mid" (Mid LogoutUser) :> 
  GetNoContent — authenticated, captures a user ID, returns NoContent.

  Two variants:
  - logout — admin logs out another user (by user ID)
  - logoutSelf — user logs out themselves (by JWT)

  Key difference from our situation: Quux has no in-memory game state to clean
  up. No agents, no scenes, no reactive network. It's stateless REST backed by
  postgres — kill the token and you're done.

  For sashamud, logout needs to do what Quux does (invalidate the session) plus
  what old sasha's removeClient does (remove from maps, notify the network). The
   REST DELETE pattern from Quux is the right shape for the route, but the
  handler body needs the channel-based cleanup because we have a Rhine network
  managing agents in memory.

❯ my concern is we have two sources of truth, there is the websocket connection 
 and there is the player in the game , consider using weak pointers or some

● That's a sharp instinct. Two sources of truth is a bug waiting to happen.

  Weak pointers won't work here — System.Mem.Weak finalizers run on GC, which is
   unpredictable in timing and not guaranteed to run at all. You can't rely on
  GC to drive game logic.

  But the underlying idea — removal at the server level automatically triggers 
  Rhine cleanup — is sound. Here's the clean way to do it:

  Poll-based detection in the Rhine network. No PlayerLeft, no acLeaveChan.

  - acPlayerMap :: MVar (Map SessionId (GID Agent)) is the single source of 
  truth for "who is currently playing"
  - Both logout handler and WebSocket close just remove from acPlayerMap (and
  acConnections). That's their whole job.
  - The Rhine network already reads acPlayerMap on every heartbeat tick. Add a
  processLeavesSF on PlayerTick that:
    a. Reads acPlayerMap to get the set of active GID Agent values
    b. Compares against PlayerAgent entries in waAgentMap
    c. Any PlayerAgent GID in waAgentMap that's not in acPlayerMap → remove from
   waAgentMap and sceneAgents

  Why this works:
  - One action (remove from acPlayerMap) → one consequence (Rhine detects
  absence, cleans up)
  - No channel to forget to write to, no race between two cleanup paths
  - Consistent with the IX pattern: GameState is output, assembled from
  accumulated state. The network discovers who left rather than being told.
  - Joins still use acJoinChan because they carry data (player name, session)
  needed to create an agent. Leaves carry no data — absence is the signal.

  Does that direction sit right with you?
